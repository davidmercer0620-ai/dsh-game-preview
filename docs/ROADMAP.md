# 路线图：游戏开发者在 DSH 里真正缺什么

这份文档不是功能清单，而是从「工作室做小游戏」的实际回路倒推出来的痛点排序。参考项目：`F:\炉石传说`（Cocos 3.8 三端小游戏 + APK）、`F:\降维联盟`（ES module + Canvas 自研）。

## 0. 现状盘点（v0.5.21 已经有的）

| 能力 | 状态 |
|---|---|
| 引擎检测（Cocos / Godot / Unity / 微信 / dev server / 静态 / 构建产物） | ✅ |
| 原生窗口捕获 + 输入转发 + 裁剪 + 画质档 | ✅ |
| PC / 手机 / 自适应设备视口，自动匹配构建 | ✅ |
| 打开即起播、按项目记忆、满屏、快捷键 | ✅ |
| Web 包 zip / Android APK（复用工程 `android/` 外壳）/ Windows EXE（需 VS+CMake） | ✅ |
| 三个 agent 工具（run / status / stop）+ 窗口枚举 | ✅ |

## 1. 痛点排序（按「每天都要碰」的次数）

### P0-1 多平台打包仍然要切终端

他们的 `cocos/tools/build-platform.mjs` 已经封装了 `wechat | douyin | taptap`，带 `validate-build-package` 与 SHA256 清单；APK 走 `android/build.sh`。但**从面板到这些脚本之间还是手动**。

**建议**：导出面板增加「工程脚本」一栏 —— 自动发现 `tools/build-platform.mjs`、`build_apk.js`、`android/build.sh`、`package.json` 的 scripts，一键执行并把输出流进面板。识别失败的工程才退回内置流程。

**价值**：最高。每个版本 3~5 次手动操作变 1 次点击。
**成本**：低（脚本已存在，只需发现 + 执行 + 流式日志）。

### P0-2 包体积是发布红线，但没人实时看

微信小游戏主包 4 MB、分包 20 MB；抖音/ TapTap 各有上限；APK 体积影响下载转化。他们现在的微信包 2.3 MB，离红线不远。

**建议**：每次构建后生成「体积报告」：总大小、每个 assets bundle 的大小、与上次构建的差值、相对平台上限的占比，超 80% 变黄、超限变红。

**价值**：高。上架被拒的常见原因。
**成本**：低-中（读构建目录 + 平台阈值表）。

### P0-3 Agent 看不到画面

现在 agent 只有 `game_preview_status`，拿不到「画面长什么样」。而他们一半的问题是视觉问题（UI 报告、战斗视觉报告）。

**建议**：新增两个工具
- `game_preview_screenshot`：把当前帧存到工程 `.dsh-game-preview/shots/` 并返回路径，agent 用 `read_image` 自查
- `game_preview_logs`：返回最近 N 行引擎/构建输出

**价值**：高。从「人描述 bug」变成「agent 自己看」。
**成本**：低（帧已经在内存里，日志也已经在 `proc.logTail`）。

### P1-1 真机预览没有入口

小游戏的验收必须真机。现在只能靠「外部打开」再自己找地址。

**建议**：预览服务暴露局域网地址 + 生成二维码（面板里画出来），手机扫码即玩；同一入口也能指向 APK 下载页。

**价值**：高（微信/抖音小游戏尤其）。
**成本**：中（局域网 IP 探测、二维码生成——可以用纯 JS 实现的极简 QR 编码器，不引依赖）。

### P1-2 构建历史与对比

每次构建的时间、耗时、体积、SHA 现在散落在 `release/build-results/*.json` 里。

**建议**：面板里一张表：最近 10 次构建，点两次可对比（体积变化、文件差异）。

**价值**：中。
**成本**：低（读他们已有的 manifest）。

### P1-3 日志面板

`/api/log` 已经返回 dev server / 引擎的 stdout，但面板没有展示。

**建议**：底栏加「控制台」抽屉，跟随滚动 + 关键字过滤；构建时自动展开。

**价值**：中高（他们排障第一现场）。
**成本**：低。

### P2-1 视觉回归

同一场景两次截图对比，UI 改动导致像素偏移时报警。

**建议**：对原生窗口（Unity/Godot）可行——截图 + 简单像素差 + 阈值；web 预览受跨域限制，只能整页截图（不可行），除非走 Cocos 构建注入。

**价值**：中，但只覆盖原生。
**成本**：中。

### P2-2 输入录制 / 回放

已经能做输入转发，把事件流 + 时间戳存下来，就能"同一段操作在两个构建上重放"。

**建议**：录制按钮 → `.dsh-game-preview/replays/*.json`；回放时按时间轴注入。

**价值**：中（做手感对比时很值）。
**成本**：中（时间轴、丢帧补偿）。

### P2-3 平衡模拟接入

他们的 `tools/headless-sim.mjs`、`p03-long-run.mjs`、`p05-long-run.mjs` 是平衡验证的核心。

**建议**：把脚本输出接进面板，画一张「10 局胜率 / 平均回合 / 经济曲线」的小图。

**价值**：高，但只对他们的数值工作流。
**成本**：中（解析输出格式需要约定）。

### P3 其它候选

- 手柄 / 多点触控
- 微信开发者工具联动（自动打开、截图、console）
- 设备矩阵预设（iPhone SE / Pixel / iPad）
- 构建失败时的「一键修」（把错误定位到文件行）
- 远程协作：把预览 URL 分享给同事（需要鉴权与隧道）

## 2. 建议的下一步（性价比排序）

| 顺序 | 功能 | 为什么先做 | 预估 |
|---|---|---|---|
| 1 | **工程脚本一键执行**（build-platform / build_apk / scripts） | 直接吃掉他们每天最多的手动步骤 | 半天 |
| 2 | **Agent 截图 + 日志工具** | 让 agent 能自查视觉，减少来回 | 半天 |
| 3 | **体积报告** | 发布红线，做了就不会被拒 | 半天 |
| 4 | **控制台抽屉** | 已有数据，纯前端 | 2 小时 |
| 5 | **二维码真机预览** | 小游戏验收刚需 | 1 天 |
| 6 | **构建历史表** | 依赖 1，顺带就能有 | 3 小时 |

## 3. 明确不做

- **WebGL 导出 Unity**：不叫预览。
- **引擎内桥接**（Godot TCP 6007 / Unity Editor 连接）：等有稳定帧源和输入通道再做，收益低于前六项。
- **跨平台窗口捕获**（macOS/Linux）：WGC 是 Windows 专有，另开工作。
- **云端真机农场**：成本与合规都不划算。
