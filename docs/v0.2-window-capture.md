# v0.2 原生窗口捕获：设计与落地状态

> 目标：让「编辑器里按 Play 跑起来的原生窗口」出现在右侧栏，而不只是一个 Web iframe。
> 状态：**PR1（抓帧）+ PR3（生命周期）已落地**；PR2（输入转发）未做。文末有实测数据与取舍原因。

## 1. 为什么值得做

Godot / Unity 的**最快回路是原生运行**，不是 Web 导出：

| 引擎 | 最快回路 | 耗时 | 走 Web 路线 |
|---|---|---|---|
| Cocos | 编辑器浏览器预览 | ~1s | ✅ v0.1 已经是 |
| Godot | F5 → 原生窗口 | ~2s | 导出 HTML5 要 5–15s，且行为不一致 |
| Unity | 编辑器 Play | ~3s | WebGL 构建 1–30 分钟，不可用 |

## 2. 抓帧：设计与实际选择

| 方案 | API | 帧率 | 兼容性 | 结论 |
|---|---|---|---|---|
| `PrintWindow(PW_RENDERFULLCONTENT)` + GDI | GDI/DWM | 20–25 fps | 窗口化 D3D11/Vulkan 都能抓，独占全屏黑帧 | **先落地** |
| Windows.Graphics.Capture | WinRT | 30–60 fps | Win10 1903+ | 预留后端，未实现 |
| DXGI Desktop Duplication | DXGI | 60 fps | 抓整屏，需处理遮挡 | 不用 |

设计文档原本把 WGC 定成默认、GDI 当兜底。实现阶段改成**先发 GDI**，原因：

1. WGC 的收益主要在"避免 40ms 的 DWM 读回"，而实测读回只有 **31ms**，真正的瓶颈是 JPEG 编码，两者都要编码；
2. WGC 要 WinRT + D3D11 的 COM 互操作（数百行无类型检查的 P/Invoke），一次性写对的概率低，而 GDI 版本当场就能验证；
3. 现在的 `host/window.js` 把抓帧后端藏在助手进程后面，换 WGC 只动 `window-capture.ps1` 内部，不改协议、不改面板。

升级判定写在代码里，供以后 WGC 用：**同一窗口连续 3 帧全黑（采样网格 98.5% 像素 < 8）才判黑**，避免误判深色场景。

## 3. 实现形态

一个常驻 PowerShell 助手（`host/window-capture.ps1`）：C# 在启动时 `Add-Type` 编译一次，PowerShell 只负责读 stdin 和写 stdout。

```
stdin :  PING | LIST | START <hwnd> <fps> <maxWidth> <quality> | STOP | QUIT
stdout:  PONG
         WIN <hwnd> <pid> <w> <h> <base64-title>          （LIST 的每一行，最后是 END）
         STARTED <w> <h>
         DATA <seq> <w> <h> <captureMs> <encodeMs> <black> <base64-jpeg>
         STAT <frames> <drops> <avgCaptureMs> <avgEncodeMs>  （每 20 帧）
         ERR <code> <message>
         STOPPED
```

线程模型：

- **抓帧线程**：`IsWindow` / `IsIconic` / 尺寸检查 → `PrintWindow` 进 32bpp 位图 → `LockBits` 拷到一个三缓冲池里的 `byte[]` → 放进"最新帧"槽位（覆盖旧帧，`drops++`）。
- **编码线程**：取槽位 → 重建位图 → 可选缩放 → JPEG → base64 → 写一行 `DATA`。
- 两个线程各自睡到目标帧率，编码慢只丢帧不积压。

Node 侧 `host/window.js`：把行协议变成 `list()` / `start()` / `stop()` / `onFrame()` / `status()`，维护最近一帧、2 秒滑窗 fps、掉帧数、断流判定（>3s 无帧即 `stale`）。助手崩溃时**自动重启一次**并按原参数续抓，再失败才把错误抛给面板。

## 4. 传输与面板

- `GET /stream` → `multipart/x-mixed-replace; boundary=frame`，`<img src>` 直接吃；空闲时每 5 秒写一个空 part，避免浏览器主动断开。
- `GET /api/frame` → 最近一帧 JPEG（204 表示超过 5 秒没有新帧），给不想长连接的客户端。
- 面板 `active.kind === 'window'` 时舞台渲染 `<img>`，左上角角标显示 `fps`、`宽×高`、`已断流`；`⏹ 停止` 同时 `taskkill /T` 和停抓帧。
- 「选择窗口」按钮：`/api/window/list` 列出当前可捕获窗口，选中后 `/api/window/attach` 接管——这条路径与引擎无关，任何窗口都能进舞台。

## 5. 窗口匹配

`launch` 后按以下顺序锁定窗口：

1. **启动进程的 PID 直接匹配**（`spawn(exe, args)` 不套 shell，所以 `child.pid` 就是引擎进程）；
2. 标题/类名通配（配置里的 `windowMatch`，例如 `Godot|Game`），作为超时前的兜底；
3. 面板上的「选择窗口」手动挑（永远可用）。

Unity 注意：Play 窗口画在编辑器窗口里的 Game 视图，所以匹配到的是编辑器主窗口——这也正是想要的画面。**Play 仍需手动按一次**：没有编辑器脚本的情况下没有可用的无头等价物。

## 6. 失败模式（已实现）

| 现象 | 判定 | 面板上的话 |
|---|---|---|
| 窗口被关闭 | 助手报 `window-closed` | 「窗口已关闭」角标，不再冻结最后一帧 |
| 最小化 | `IsIconic` 为真 | 「窗口最小化时无法捕获，请还原窗口」 |
| `PrintWindow` 失败 | 返回 false | 「这个窗口抓不到画面（常见于独占全屏），请换成无边框窗口」 |
| 连续全黑 | 3 帧采样判黑 | 「连续全黑帧：可能是独占全屏，或游戏刚启动还没画第一帧」 |
| 没有帧 > 3 秒 | Node 侧滑窗 | 「已断流」角标 |
| 助手崩溃 | 进程 exit | 静默重启一次并续抓；再失败报错 |
| 找不到窗口 | 30s 超时 | 「没找到游戏窗口：确认引擎已启动；Unity 还要按一次 Play，或用『选择窗口』」 |
| 引擎没装 | 路径解析失败 | 点名要填 `godotExe` / `unityExe` |

## 7. 实测数据

机器：Windows 10 22H2（19045），Intel/NVIDIA 混合 + 向日葵虚拟显示器。

| 目标 | 窗口尺寸 | 抓帧 | 编码 | 端到端 |
|---|---|---|---|---|
| Chrome（D3D 合成，后台窗口） | 1691×995 | 31 ms | 17 ms | **25.4 fps / 97 KB 每帧 / 0 掉帧** |
| 记事本（GDI） | 1288×723 | ~20 ms | ~10 ms | 16 fps |
| 同上，串行实现（无流水线） | 1691×995 | 31 ms | 17 ms | 12.6 fps |

结论：流水线是这版 fps 翻倍的原因；JPEG 编码和抓帧各占一半，所以 `captureWidth` 是主要的提速旋钮（缩放本身也吃 CPU，1280 以上才值得开）。
